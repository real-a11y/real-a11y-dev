# Semantic Navigator — Chrome Extension

Chrome extension that adds a Side Panel with an interactive DOM/accessibility tree view for any web page.

## Installation

[Install from the Chrome Web Store](https://chromewebstore.google.com/detail/semantic-navigator/gnnepgbbecnlomngfemkadnbeaopleom).

> **Note on the install warning.** Chrome may show *"Proceed with caution — not trusted by Enhanced Safe Browsing"* before install. ESB classifies new extensions as untrusted by default until Google's systems have built enough signal on the listing; the notice is unrelated to anything specific in this extension. Click **Continue to install**.

## Installation (from source)

1. Clone the [monorepo](https://github.com/real-a11y/real-a11y-dev) and build the extension:
   ```bash
   git clone https://github.com/real-a11y/real-a11y-dev.git
   cd real-a11y-dev
   pnpm install
   pnpm --filter "@real-a11y-dev/semantic-navigator-extension..." build
   ```
2. Open `chrome://extensions` in Chrome
3. Enable **Developer mode** (toggle in the top right)
4. Click **Load unpacked** and select the `packages/extension/dist` directory
5. Navigate to any web page and click the Semantic Navigator icon in the toolbar

## How it works

### Architecture

```
Side Panel (Preact UI)
    ↕ chrome.runtime messages
Background Service Worker
    ↕ chrome.tabs messages
Content Script (runs in page context)
    ↕ DOM APIs
Web Page
```

- **Content Script** — Injected into every page, and every frame of it. Extracts the DOM/accessibility tree using `@real-a11y-dev/core`, dispatches actions on real DOM elements, manages the highlight overlay, and applies native Tab / Escape defaults for the panel keyboard bar (Tab reuses core `getTabSequence`; synthetic key events alone cannot move focus or close `<dialog>`). A page can replace its document without navigating (`document.open()`, which is how a blank frame gets its content): that detaches the root element the tree is read from and removes every listener the script had, so the script binds to the document again whenever its root element changes, and draws the screen curtain again if it was up.
- **Background Service Worker** — Routes messages between the Side Panel and content scripts, and merges each frame's tree into one, each under the `<iframe>` that holds the frame. A frame of its parent's origin says which that is itself (see Frames with no URL of their own below); any other is matched by comparing its URL with each `<iframe>`'s `src`. Every frame Chrome lists takes the `<iframe>` its URL names exactly, then each one left the `<iframe>` it names but for the query string, and only then is a frame that matched nothing put under the first empty `<iframe>`, as a last resort. A hidden frame's `<iframe>` (a tracker's, a collapsed ad slot's) has no node in the tree, so its URL names none exactly; because every URL match comes first, such a frame loading before an embed the page shows can't take the embed's place. Because that per-frame state is in memory only, it also originates traffic of its own: when Chrome restarts it under a loaded page it asks frames it has no tree for to re-announce, so the panel doesn't lose its iframe subtrees. Manages the Side Panel lifecycle. Panel→content commands carry the panel's bound `tabId`; the background prefers that over its global `activeTabId` so a tab-switch race cannot land `DISPATCH_ACTION` / `SEND_KEY` / `CLOSE_TAB` on the newly active tab while the panel still shows the previous tab's nodes.
- **Side Panel** — Renders the tree UI. Receives serialized tree data from the content script and sends action commands back. Each Chrome window has its own, which shows that window's active tab and no other window's: it asks for that tab itself when it opens (the active tab of its `currentWindow`), and after that the service worker tells it of each switch, naming the window it is for (`ACTIVE_TAB_CHANGED`, `panelWindowFor` in `src/routing.ts`). A popup, such as a login window, has no side panel of its own: when the user moves to one, the panel of the ordinary window they were in shows it until it closes (`TAB_CLOSED`), a tab is switched to in that window, or they move to that window's page, from another window or from the panel. Moving to the panel itself, to read the popup or close it, leaves it on the popup. A **Copy ▾** dropdown exports the current view to the clipboard as a paste-ready Markdown accessibility report — Everything, the A11y/DOM tree, the heading outline, or the tab sequence — for dropping into a bug tracker. On the native tree it offers Everything, the native tree and Headings (no tab sequence: Chromium's tree has no tab order); every report's header names the producer that built it. The keyboard bar (`Esc` · `Tab` · `Shift+Tab` · `Enter` · `Space` · `↑` · `↓`) sends keys to the focused page element. Native mode, on by default and turned off in **Settings ▾**, switches the producer to Chromium's own accessibility tree over `chrome.debugger` instead of the content script's DOM walk — see Native mode below. In either tree a name longer than the panel is wide ends in an ellipsis, carrying its whole text as a tooltip, so the tree fits the panel; **Settings ▾** → **Show full names** widens the tree to fit names instead, in every window's side panel (`settings.showFullNames` in `chrome.storage.local`).

### Permissions

| Permission      | Why                                                                                                                                                                |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `activeTab`     | Access the current tab's DOM for tree extraction                                                                                                                |
| `sidePanel`     | Register and open the Side Panel UI                                                                                                                             |
| `webNavigation` | Detect SPA route changes so the tree refreshes when the page does                                                                                               |
| `debugger`      | Powers native mode (below): reads and acts on Chromium's own accessibility tree over CDP. Required by the manifest for every install, since `chrome.debugger` cannot be an optional Chrome permission. Native mode is on by default and attaches only while the side panel reads or acts on the page it shows; turned off in the panel's Settings, it never attaches. |
| `tabs`          | Lets native mode read the URL of the tab the side panel is bound to, to tell whether Chrome lets the debugger attach there (it can't on `chrome://` pages or the Web Store) and whether the page has navigated since the tree was read. Chrome has no way to grant `tabs` for a single tab, so this is technically broader than that use (it could read the URL and title of any open tab); the code reads only the bound tab's, and never enumerates others |
| `storage`       | Persists the side panel's settings locally: whether native mode is on, **Follow page changes**, and whether the note about Chrome's debugging bar was dismissed. For the browser session only, it also keeps content-free bookkeeping about a native-mode attachment (which tab, since when) while one is up, and which tabs have the screen curtain on, so closing the panel still lifts it after Chrome stops the service worker |

The content script is declared in the manifest with `<all_urls>` and `all_frames: true` so the tree is ready the moment the user opens the side panel. No data leaves your browser; the extension makes no network requests.

### Frames with no URL of their own

The content script's `match_about_blank: true` also runs it in the `about:blank` and `srcdoc` frames of a page it runs in, and so in the frames a script writes into, which is how rich-text editors and many ad slots are built. It changes which frames get the script and nothing about what the extension may access: Chrome derives an extension's host access, and the install warning, from `matches` alone, so this adds no permission and no re-consent on update.

`match_origin_as_fallback` is deliberately not set. It would add sandboxed frames without `allow-same-origin`, and `data:` and `blob:` frames, and those can't be placed: their origin is their own, so a script there can't reach the `<iframe>` that holds its frame, and Chrome's `webNavigation` lists no `blob:` frame at all. No content script runs in them, the in-page tree shows their `<iframe>` with nothing inside, and Focus sync doesn't follow focus into them. Chrome's tree still reads them.

Nothing in a URL tells these frames apart. They all show `about:blank` or `about:srcdoc`, their `<iframe>`s carry no `src`, and a frame a script wrote into reports the URL of the document that wrote it. So each frame's content script marks the element holding its frame, and the script of the document around it reads the mark off that element (`src/frame-owner.ts`). A frame of its parent's origin can read `window.frameElement`, and one extension's content scripts see the same object for the same element in every frame of an origin, so a property set on it by one is there for the other. Page script has objects of its own for the page's elements and never sees it, and nothing reaches the DOM. The mark goes with a frame's tree (`FRAME_TREE_DATA`), with the nodes of its tree that bear one, and the merge places a marked frame by its mark alone. A marked element the tree has no node for, as the a11y view has none for a hidden `<iframe>`, is reported with no node, and its frame stays out of the tree. A frame whose mark no tree bears yet is never placed by a guess, and while one is waiting no other frame under the same parent is either: the empty `<iframe>` a guess would take may be the waiting frame's. That lasts until the document around them has answered: a frame still unplaced then is held by an element the tree has no node for (a hidden `<iframe>` inside a shadow root), which no guess can take. The tree of the document around it usually arrives within moments, as a page that adds a frame changes; when none has after a second and a half, the service worker asks that document for its tree again, once.

### Native mode

On by default. The side panel's own DOM/A11Y tree (above) is this extension's own in-page ARIA/AccName walk; native mode instead reads **Chromium's own** accessibility tree over `chrome.debugger` — the same protocol DevTools uses — which sees things the DOM walk can't (UA-shadow content like native media controls) at the cost of Chrome's bar reading “Semantic Navigator” started debugging this browser, shown across every window while attached. The first time the panel reads a page this way, a one-time note explains that bar, with **Got it** and **Turn off**. **Settings ▾** → **Read pages through Chrome (recommended)** turns it off or back on later, in every window's side panel at once: the setting is `settings.nativeModeEnabled` in `chrome.storage.local`, and it reads as on unless it is `false`. While it is on, **Show** below it switches this panel between **Chrome's tree** and the **In-page tree**, whose DOM / A11Y / TAB views are in the toolbar; that choice is per panel, and not stored. Chrome's tree has A11Y / TAB views of its own: Chromium's tree carries no tab order, so its TAB view lists the content script's tab stops (`TabSequenceView`, as in the in-page tree), and selecting or activating one goes through the content script too, so it never attaches the debugger. The two trees share which view shows. A pick from the page, which selects a row in Chrome's tree, switches it back to A11Y. Turning it off detaches as soon as any read or action already under way finishes. See `DOGFOOD.md` for the exercise that validated shipping this, and [Two producers](https://real-a11y.dev/guide/reading-the-a11y-view#two-producers) for how the DOM and native producers relate.

With it on, each time you open the side panel it shows the native tree for the first page that connects, with no click: that first page attaches the debugger by itself. After that, switching tabs doesn't attach on its own; the native tree's ↻ button reads the new tab, as does choosing **Chrome's tree** in Settings from the in-page tree. If native mode can't read that first page (DevTools already has it open, say), the panel stays on the in-page tree, says why, and tries the next tab you switch to instead.

Once a read has succeeded on a tab, the native tree follows that tab across navigations: the new page is read once, after its content script reports it. An action or a sent key reads the page again a quarter second later, and for five seconds after that read (`ACTION_FOLLOW_MS`) every burst of page changes is read as soon as the page goes quiet, with no gap or back-off: a reaction that waits on the network lands after the first read. A navigation that starts in those five seconds, such as one a click sets off a second later, carries them to the page it leads to, from that page's first read. The user clicking, or pressing `Enter` or `Space`, on the page itself opens the same five seconds, from the moment it happens, with no read of its own, and a navigation it starts carries them as an action's does (`src/page-input.ts`). Only the browser's own events count, never a script's, the extension's included: not a `submit`, which the browser fires as its own for a script's `requestSubmit()`, nor the click a script's click on a `<label>` makes it fire on the label's control. Typing isn't followed. A click that puts the caret in a text field or an editable region doesn't count: a read-only field isn't one (a date picker or a custom select opens on it instead), and a date or time field is one, typed into where it is clicked. Nor does `Enter` in a `<textarea>` or an editable region, where it starts a new line, even on a page that makes it send a message instead, nor either key while an IME composes. `Space` counts only on a control that takes it, by its role: the one the tree gives it, or the first one its author wrote, since a wrapper with no role of its own may sit between it and the composite it needs; a cell only in a grid, as a date picker's days are. It is counted on the key, since a menu button often acts on it and cancels the click, but not on a `<select>`, where Space is part of what the user types to find an option; anywhere else it types or only scrolls. A closed shadow root's field is found through `chrome.dom.openOrClosedShadowRoot`, as for Focus sync. Once the user types, the window ends where they did (`followTyping`): the content script sends `PAGE_TYPING` for each edit of text the browser makes for the user (an `input` event with an `inputType`, which a checkbox, a select or a slider changing value doesn't have), with only when: when the edit was made (`at`), by the clock its changes are dated by, so a change the typing made is never dated inside the window it ends however late the panel hears of it, and when the user pressed the key that made it (`pressedAt`, `typingClock`: the key the page dispatched last, within half a second and with no press of the pointer since), which a frame busy as they type dispatches later. What the window followed before that is still read; what the typing does after it isn't, so the bar doesn't come up as the user types after a click elsewhere, or after `Enter` in a search field. A window a read opens ends where the user typed while the read ran (only its action part, if they clicked on the page after typing), and the page a navigation is leading to isn't followed once they type there. No report is held back: a throttle per frame would let typing after a click in another frame (an editor in an `<iframe>`, its toolbar in the page) be followed. A later navigation carries a destination already set only as a redirect would: within five seconds of the hop before, and only if the user hasn't typed since, so one that never committed (a download) doesn't carry it to a later page. Five limits remain: a change the page makes within the observer's 300 ms debounce before the user starts typing is flushed with the typing and dated by it, so it isn't followed; typing into a date or time field, which the browser reports as a plain `input` event, isn't seen as typing; a date picked from such a field's own picker isn't followed, since the click that opens it can't be told from a click to type; an edit that the page's own handling of its key holds up for more than half a second is ordered against a click by when it was made, not by its key; and a toolbar button that edits text through `document.execCommand`, such as an editor's Bold, makes the browser report the edit as the user's own, so it ends the click's window as typing does. A press of the pointer opens no window: a read while it is held, in a drag, would bring Chrome's bar up and move the page under the pointer. So a menu that opens as it is pressed is followed when the click comes before its change is heard of, about half a second, and not after a slower press. Nor is any of it while auto-refresh is paused. The window's reads keep `AUTO_REFRESH_MIN_GAP_MS` after the read before them, with no back-off, where an action's are read at once: the user clicks on the page far more often than through the tree, and not always for the tree, and a page that also changes by itself would otherwise be read on its every burst after every click. `src/sidepanel/follow-window.ts` keeps the window's bookkeeping: where it starts and ends, which part an action opened, the window a click closed (whose changes reported late still count), and what a navigation carries to the page it leads to. While a panel observes the frame, its content script sends `PAGE_INPUT`, which carries only when the user acted (`at`, the event's own time, `actedAt`): not what was clicked or typed, nor where. The panel orders a click and typing by when the user did them (a click's `at`, a key's `pressedAt`), not by whose report reaches it first, since a frame busy when the user acts reports it late: a click the user typed after, in another frame, opens nothing, and a key pressed before the latest click doesn't end the window, only an action's part, which no click opens, so the edits a busy frame makes after the click for keys pressed before it are read with what the click does. An edit made just before a click and reported after it is followed as the click's, as any such change is. Where the clock has stepped back since, the panel can't order them: a click opens its window, and typing ends it. Like `LIVE_REGION` it reaches the panel straight from the content script, scoped by `sender.tab.id`, and the service worker doesn't relay it. Nothing reads the page for it, so every change the panel had already heard of was made before it and isn't its own: the window it opens starts after them, where an action's starts with its re-read, which saw them. Other page changes wait for ↻, unless **Follow page changes** is on (the native toolbar's ⟳ toggle, `settings.nativeFollowPageChanges` in `chrome.storage.local`); then every burst of changes is read once the page goes quiet, backing off the longer it runs without the user. A burst counts when it is in the top frame or in a frame the page shows (`frameVisibility` in `src/frame-merger.ts`), so a hidden frame's changes, an animating ad's, never prompt a read. Each changed tree carries when its frame changed (`changedAt`, stamped by the content script), and the service worker passes those the page shows to the panel as `pageChangedAt`: a read that started after a change saw it, however late the signal arrived, and an action is followed while any change the panel hasn't read falls in its five seconds. A tree a frame sends again on request, or after an action or a key (`reread`), isn't a change at all. `src/sidepanel/native-auto-refresh.ts` holds the policy. A tab switch disarms it until ↻, and so does a failed read, so a refusal is never answered by another attach. The user's **Cancel** on Chrome's debugging bar pauses it whatever it interrupted — a pick, an action, a refresh — because the background refuses automatic reads on that tab until the user reads it again; that pause lives in the service worker's memory and lapses if Chrome restarts it.

Focus sync follows page focus in the native tree too, with no debugger attach. While it is on, each native read (`NATIVE_READ` with `pageKeys`) numbers every document's elements twice, the top document's and each frame's: over CDP (`DOM.getDocument`, in the session that document is read through) and in the content script's own walk of its frame's live document, both with `src/native/page-keys.ts`, and gives a document's rows those numbers only if its two walks agree. The extension's frame ids and CDP's frame tokens can't be turned into one another, so a frame's document is matched to its frame one of two ways. A frame of its parent's origin marks the `<iframe>` holding it (see Frames with no URL of their own above), its parent's walk reports that element's number with the mark, and CDP's walk gives the same element the same number: the document under it is the one of the frame that answered with the mark, or nobody's. This is the only way a frame the tab lists at an `about:` URL is matched. Any other frame is matched by URL: to the frame whose content script numbered a document at the same URL to the same digest, and only when that frame is the only one showing that URL, answered or not. Of two such frames showing the same page, either could be showing a document read at it, so neither is numbered. A frame's document that has the URL of another document in its renderer may be one a script wrote, whose frame is listed at `about:blank` whichever frame answered at the URL. It is matched by URL only to a frame the tab lists as a child of the frame around it (`parent`, set from `getAllFrames`), and only when it is the one document at that URL inside the document around it: a child at that URL shares the renderer, so its own document is among those read, and of two neither is matched. Only frames the content script can run in are asked (`http:`, `https:`, `file:`, `about:`, and no error page), at most 32: the frames the read put in the tree first, then those with no URL of their own, which a URL can't say are in it. A frame in the tree gets as long as the top frame to answer; once the top frame has answered, the read's own walks are in and the frames are listed, any other gets a quarter of a second more, and one still busy by then goes unnumbered until a read it answers. A frame's rows carry its frame id (`pageFrame`), and its `Iframe` row the frame it shows (`embedsPageFrame`). The content script keeps each element's number by identity and reports page focus by it, the service worker adds the reporting frame, and the panel looks the numbers up among that frame's rows, so a row is found for the focused element whatever the page has done since the read; a listener on each shadow root focus has been in hears the moves inside it, which never reach the document. Focus on an element with no row above it in its frame selects the frame's `Iframe` row. After a page writes a frame's document over again, none of its elements were there to be numbered, and focus inside it selects the frame's `Iframe` row until the next read. A frame no content script runs in (a sandboxed frame without `allow-same-origin`, a `data:` or `blob:` frame) isn't numbered, so focus inside it isn't followed. The service worker re-asserts the Focus sync toggle to every frame that announces itself as the panel last set it for that tab, so **Focus OFF** holds through page updates.

Chrome still blocks content scripts outright on some pages — `chrome://` pages (including the default new-tab page), the Chrome Web Store, and the built-in PDF viewer. A panel→content broadcast there reaches no frame, and the background reports that back (`{ success: false, error: "restricted-page" }`) rather than claiming delivery. Any tree request that comes back that way — the panel's first load, the `↻` refresh, **Load tree** — puts the panel in a **This page can't be inspected** state instead of leaving it waiting on a tree that can never arrive.

Reaching such a page by switching tabs or by navigating does not show that message on its own; it empties the panel first. A tree only ever reaches the panel because a frame announced one, and on these pages none ever will, so the background pushes `PAGE_NAVIGATED` on every top-frame navigation and the panel drops what it holds. Keeping the old tree would be worse than an empty one: node ids are a per-frame counter, so its rows resolve to unrelated elements on the new page while staying clickable. From there **Load tree** answers honestly.

### Content Security Policy

`extension_pages` is locked to `script-src 'self'; object-src 'self'; base-uri 'self'` — the side panel cannot load remote scripts, embed `<object>`/`<embed>` from third parties, or be re-based to a different origin. See `public/manifest.json`.

### Versioning

`public/manifest.json`'s `version` is the source of truth shipped to the Chrome Web Store. It's kept in sync with `package.json` automatically by `scripts/sync-manifest-version.mjs`, which runs as `prebuild`. CI runs the same script with `--check` (via `pnpm typecheck`) and fails if the two have drifted.
