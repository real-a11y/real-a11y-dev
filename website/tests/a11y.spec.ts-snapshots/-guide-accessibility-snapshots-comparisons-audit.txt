  heading "How Accessibility Snapshots Compare" (level 1)
  paragraph
    text "An"
    link "accessibility snapshot"
    text "doesn't replace your other accessibility and regression tools — it sits beside them and covers a blind spot each of them has. This page walks through the four it's most often confused with, and where the lines fall."
  paragraph
    text "The throughline is"
    strong "jsdom"
    text ". Because Real A11y computes its own accessibility tree, the"
    emphasis "same"
    text "snapshot runs in a millisecond-fast Vitest/Jest unit test"
    strong "and"
    text "in a real browser. The other tools below either need a real browser to read its native accessibility tree, or answer a different question entirely."
  heading "Versus visual regression testing" (level 2)
  paragraph
    text "Screenshot testing — Playwright's"
    code "toHaveScreenshot()"
    text ", or services like Percy, Chromatic, and Argos — is the other great snapshot discipline, and it's genuinely complementary. A visual snapshot renders the page to pixels and diffs the image: when a layout shifts, a color regresses, or a component visually breaks, the diff lights up the exact region and you spot it instantly. For"
    emphasis "appearance"
    text ", nothing beats it."
  paragraph
    text "But pixels only describe what a sighted, mouse-using visitor sees. A screenshot can be pixel-perfect while the page is broken for assistive technology — and those failures move"
    strong "zero pixels"
    text ":"
  list
    listitem
      text "A real"
      code "<button>"
      text "swapped for a"
      code "<div onclick>"
      text "styled to match — identical screenshot, gone from the a11y tree."
    listitem
      text "An icon button that lost its"
      code "aria-label"
      text "— looks the same, now announces nothing."
    listitem
      text "A heading restyled into a plain"
      code "<span>"
      text "— same font size on screen, vanished from the outline."
    listitem "Focus order rearranged by a layout change — visually unchanged, keyboard path now illogical."
  paragraph "None of these show up in a screenshot diff. Every one shows up in an accessibility-snapshot diff. The reverse holds too: a purely visual regression — a broken gradient, an overlapping panel, a spacing bug — won't move an accessibility snapshot."
  paragraph
    text "So they're the two halves of regression testing:"
    strong "how it looks"
    text "and"
    strong "what it means"
    text ". A mature suite runs both — visual snapshots for appearance, accessibility snapshots for semantics — and neither one covers the other's blind spot."

  heading "Versus Playwright ARIA snapshots" (level 2)

    text "instead of markup. If your tests already run in a real browser through Playwright, it's an excellent first-party tool — reach for it."

  paragraph
    text "The practical wedge is jsdom. jsdom has no accessibility tree, so a snapshot built on the browser's AX tree simply can't run in a Vitest or Jest unit test. Because Real A11y computes its own tree, the"
    emphasis "same"
    text "snapshot runs in a millisecond-fast unit test and in a real-browser E2E run — and matches what you inspect by eye in the panel."

  heading "Alongside real screen-reader testing" (level 2)
  paragraph "This complements real screen-reader testing — it doesn't replace it"
  paragraph
    text "Nothing substitutes for hearing your app announced; lived AT experience catches things structure alone can't. What snapshots do is move the first and largest class of problems —"

    text "ones — to where every developer already works: a diff in code review. Deep expertise becomes a way to go further, not the price of entry."
