  heading "Semantic Navigator" (level 1)
  paragraph "Navigate the web the way your users have to."
  paragraph "Most accessibility problems don't look like problems — until you remove the visual layer. Semantic Navigator replaces the page with its accessibility tree. You can still click, navigate, fill forms, and complete tasks. The structure is all you get."
  link "Add to Chrome"
  link "View on GitHub"
  figure
    img "A browser with the Semantic Navigator screen curtain turned on: the left half of the window is fully blacked out and labeled “Content hidden — navigate via Semantic Navigator,” while the side panel on the right shows the page's complete accessibility tree — banner, main navigation, breadcrumb, headings, and links and buttons with their roles and accessible names — still fully navigable, with a keyboard-key bar along the bottom."

  heading "The test" (level 2)
  paragraph
    strong "If you can complete the task through the accessibility tree, your users probably can too. If you can't, that's the bug."
  list
    listitem
      strong "Open the side panel."
      text "Click the extension's icon in the Chrome toolbar. The panel opens next to the page and shows its tree."
    listitem
      strong "Turn on the curtain."
      text "The"
      strong "Curtain"
      text "button in the panel's toolbar blacks out the page. The tree and every interaction stay."
    listitem
      strong "Do a real task through the tree."
      text "Check out, book an appointment, find the error after a failed submit, close the dialog that just opened. Select a row and press"
      code "Enter"
      text "to act on it."
    listitem
      strong "Stop where you get stuck."
      text "A button you can't find, a control you can't tell the purpose of, an action you can't tell worked: that's the bug your screen reader users hit."
  paragraph "The panel shows the tree screen readers read, not what NVDA, JAWS, VoiceOver or TalkBack say or how they move through a page. Use it to catch missing names, wrong roles and broken tab order early, and test with real screen readers before you ship."
  heading "Chrome's tree" (level 2)
  paragraph
    text "The panel reads Chromium's own accessibility tree, the one Chrome gives assistive technology, over"
    code "chrome.debugger"
    text ". It sees what a reading of the page from inside it can't, such as a video player's built-in controls. Where Chrome won't let it read a page, with DevTools open on the tab, say, the panel says why."
  paragraph
    text "While it reads, Chrome shows a bar across every window: “Semantic Navigator” started debugging this browser. That's expected. Pressing"
    strong "Cancel"
    text "on the bar stops the panel reading that tab until you press"
    strong "↻"
    text "."
  paragraph
    text "Chrome's tree is read when the panel opens, when the page navigates, and for a few seconds after you act. For any other change press"
    strong "↻"
    text ", or turn on"
    strong "Follow page changes"
    text "("
    strong "⟳"
    text "). It has no tab order of its own, because"
    code "tabindex"
    text "never reaches a native node, so its"
    strong "TAB"
    text "view, next to"
    strong "A11Y"
    text "in its toolbar, lists the tab stops of the extension's own reading of the page, in tab order, as"
    link "the TAB view"
    text "of the other panels does: a positive"
    code "tabindex"
    text "first, then document order. A frame is one stop where Tab enters it. Neither models shadow roots, focus traps or keyboard-focusable scrollers. Showing it reads nothing through Chrome, so the bar doesn't come up for it, and it works on a page Chrome's tree can't read. It takes a moment to read the page as it comes up. Chrome's tree and the other panels' trees never match exactly, by design: see"
    link "Two producers"
    text "."
  paragraph
    text "Up to version 0.1.17,"
    strong "Settings ▾"
    text "could switch the panel to the extension's own in-page tree, with its DOM view. Chrome's tree is the only one now."
