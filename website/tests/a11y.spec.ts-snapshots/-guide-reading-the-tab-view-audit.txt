  heading "How tab order works" (level 2)
  paragraph "Browsers determine tab order using two rules, applied in this sequence:"
  list
    listitem
      text "Elements with a"
      strong
        text "positive"
        code "tabindex"
      text "(like"
      code "tabindex="1""
      text ","
      code "tabindex="2""
      text ") come first, sorted from lowest to highest. Elements with the same value are sorted by their position in the document."
    listitem
      text "Everything else — elements with"
      code "tabindex="0""
      text "or no tabindex at all — follows in"
      strong "document order"
      text "(top to bottom, left to right)."
  paragraph
    text "Elements with"
    code "tabindex="-1""
    text "are completely excluded. They're reachable programmatically (via JavaScript's"
    code ".focus()"
    text "), but invisible to the Tab key."
  paragraph
    text "A"
    code "tabindex"
    text "outside the signed 32-bit range (such as"
    code "tabindex="2147483648""
    text ") is ignored as if it were absent, and an element with"
    code "display: contents"
    text "has no box, so neither is listed as a stop. Focusable children of a"
    code "display: contents"
    text "element stay in the sequence. Chrome decides both; the HTML Standard leaves rendering to the browser."
  paragraph "The TAB view reflects this computed order exactly."

  heading "What to check" (level 2)
  heading "Order matches the visual flow" (level 3)
  paragraph "Tab order should feel predictable. A user who can see the page expects focus to move left to right, top to bottom — the same way they'd read it. If someone tabs through a navigation bar and focus jumps to the footer before reaching the main content, something is wrong."
  paragraph
    text "Compare the TAB view numbers to the visual layout of your page. If a"
    code "position: fixed"
    text "header contains the skip link at number 1 and the search field at number 2 — but the search field appears after a hundred nav items visually — keyboard users are in for a confusing ride."
  heading "Every interactive element is reachable" (level 3)
  paragraph "Scan the list. Does every button, link, input, select, and interactive control appear? If something is missing, keyboard users can't reach it."
  paragraph "Common reasons an element is absent:"
  list
    listitem
      text "It's a"
      code "<div>"
      text "or"
      code "<span>"
      text "with a click handler but no"
      code "tabindex"
      text "or"
      code "role"
      text ". It's mouse-only."
    listitem
      text "It has"
      code "tabindex="-1""
      text "— reachable by script, but not by Tab."
    listitem
      text "It has"
      code "display: none"
      text ","
      code "visibility: hidden"
      text ", or"
      code "aria-hidden="true""
      text "."
    listitem
      text "It sits in the body of a closed"
      code "<details>"
      text ". The browser renders a closed disclosure as its summary alone, so the rest is out of the tab order until it opens."
    listitem
      text "It has the"
      code "disabled"
      text "attribute (disabled elements are correctly excluded from tab order)."
  heading "Nothing unreachable appears in the list" (level 3)
  paragraph "The opposite problem: elements that show focus but shouldn't. A visually hidden element that's still in tab order means keyboard focus will land somewhere invisible — and the user will have no idea where they are."
  paragraph "This often happens with off-screen drawers or modals that haven't been properly hidden from the accessibility tree while closed."
  heading "Amber badges — positive tabindex" (level 3)
  paragraph
    text "If you see"
    code "tabindex=2"
    text "or"
    code "tabindex=5"
    text "badges, that's almost always a mistake. Here's why:"
  paragraph "Positive tabindex values pull elements to the front of the tab queue, ahead of everything else in the document regardless of where they appear in the markup. The result is that focus jumps around the page in an order that doesn't match anything visual — disorienting for any keyboard user."
  paragraph
    strong "The fix is to reorder the DOM"
    text ", not to manage tab order through"
    code "tabindex"
    text "values. Put elements in the document in the order you want them to be focused. Then tab order is natural and requires no maintenance."
  paragraph
    text "The only legitimate use of"
    code "tabindex="-1""
    text "is for programmatically managing focus (e.g., moving focus into a modal when it opens). Positive values beyond that are a code smell."
  heading "Focus traps inside modals and dialogs" (level 3)
  paragraph "When a dialog is open, Tab should cycle only through elements inside it — it should never escape to the content behind. The TAB view will show you all focusable elements, so you can check whether the dialog contains everything it should and whether elements behind it are visible in the list when they shouldn't be."
  paragraph "A correct focus trap:"
  list
    listitem "Contains all interactive elements in the dialog"
    listitem "Wraps from the last element back to the first when Tab is pressed at the end"
    listitem "Returns focus to the trigger element when the dialog closes"

  heading "The relationship to the A11y view" (level 2)
  paragraph "The TAB view and the A11y view are complementary. A11y shows you structure and labeling — whether elements have correct roles and names. TAB shows you reachability and order — whether keyboard users can get to those elements at all."
  paragraph "An element can have a perfect role and accessible name in the A11y view but still be unreachable if it's not focusable. Conversely, an element can appear in the TAB view with no useful name. You need both to get the full picture."
