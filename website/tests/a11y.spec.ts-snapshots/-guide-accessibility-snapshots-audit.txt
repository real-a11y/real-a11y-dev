  heading "Accessibility Snapshots" (level 1)
  paragraph
    text "An"
    strong "accessibility snapshot"
    text "is a deterministic, human-readable capture of what assistive technology perceives on a page — roles, accessible names, heading outline, and tab order — serialized to a string you can commit and diff in code review."
  button "Copy Code"
  code "main heading "Sign in" (level 1) form "Sign-in form" textbox "Email" button "Sign in""
  paragraph
    text "It's the structural counterpart to rule-based audits. Where a tool like"
    link "axe"
    text "answers"
    emphasis ""does this violate a WCAG rule right now?""
    text ", an accessibility snapshot answers"
    emphasis ""what is the semantic structure — and did it change?""
    text "For how it stacks up against axe, visual regression testing, and Playwright's ARIA snapshots, see"
    link "How Accessibility Snapshots Compare"

  heading "Why this exists" (level 2)
  paragraph
    text "Accessibility is hard to get right. Building — and"
    emphasis "testing"
    text "— an accessible web app demands fluency in WCAG, ARIA, and the accessible-name algorithm, plus the quirks of real screen readers, which behave differently across NVDA on Windows, VoiceOver on macOS and iOS, and TalkBack on Android. That's a steep wall, and it's a big reason teams ship accessibility bugs they never notice."
  paragraph
    text "An accessibility snapshot lowers the bar. Because it shows your page exactly as assistive technology structures it — roles, names, headings, focus order — you can read it and answer the questions that matter"
    emphasis "without"
    text "being a screen-reader expert:"
  list
    listitem
      emphasis "Does this snapshot match what I think my page contains?"
    listitem
      emphasis "Would this structure make sense to someone who can't see it?"
    listitem
      emphasis "Is anything unlabeled, mis-roled, or out of order?"
  paragraph
    text "You don't need NVDA, VoiceOver, and TalkBack open across three machines to catch a missing label or a heading that jumps from"
    code "<h1>"
    text "to"
    code "<h3>"
    text ". You read the snapshot in your editor, or in a pull-request diff. It doesn't"
    emphasis "replace"
    text "real screen-reader testing —"
    link "more on that"
    text "— it moves the largest, most mechanical class of problems to where every developer already works."
  heading "The problem with DOM snapshots" (level 2)
  paragraph
    text "A normal"
    code "toMatchSnapshot()"
    text "on rendered HTML captures the"
    strong "DOM"
    text ": every wrapper"
    code "<div>"
    text ", class name, and inline style. Two problems follow:"
  list
    listitem
      strong "Noise."
      text "A purely visual refactor — renaming a class, nesting another"
      code "<div>"
      text "— churns the snapshot even though nothing a screen-reader user perceives has changed."
    listitem
      strong "Blind spots."
      text "The DOM snapshot says nothing about the"
      emphasis "accessible name"
      text "computed from"
      code "aria-labelledby"
      text ", whether headings skip a level, or what order elements receive focus."
  paragraph
    text "An accessibility snapshot inverts both. It captures"
    strong "only"
    text "what reaches the accessibility tree — the tree at the top of this page — so it's stable against cosmetic change and surfaces exactly the semantics that matter. Rename every wrapper class and the snapshot is byte-identical. Drop the form's"
    code "aria-label"
    text ", skip from"
    code "<h1>"
    text "to"
    code "<h3>"
    text ", or leave a button unlabeled — and it changes immediately."

  heading "Deterministic by construction" (level 2)
  paragraph
    text "The same DOM always produces the same string — no timestamps, generated IDs, or ordering surprises — so"
    code "toMatchSnapshot()"
    text "is safe in CI without flakes. For genuinely dynamic content (timestamps, tokens, currency),"
    link "redact"
      code "redact"
    text "replaces the noisy bits while keeping the structure intact:"
  button "Copy Code"
  code "expect( treeSnapshot(container, { redact: [/\d+ (minutes?|hours?) ago/] }), ).toMatchSnapshot();"
  heading "It models real AT behavior" (level 2)
  paragraph
    text "Because the snapshot reflects the"
    emphasis "extracted"
    text "accessibility tree — not raw markup — it captures semantics a DOM dump can't. The clearest example is"
    strong "modal scoping"
    text ": when a dialog is genuinely modal, content behind it is inert to assistive tech, so it drops out of the tree. Open a modal and the snapshot (and tab order) collapse to just the dialog — a precise artifact for that state. "Genuinely modal" follows Chromium's own accessibility tree: a"
    code "<dialog>"
    text "opened with"
    code "showModal()"
    text ", or a page that makes the background"
    code "inert"
    text "or"
    code "aria-hidden"
    text "the way modal libraries do."
    code "aria-modal="true""
    text "on its own is only a hint, and the page behind it stays in the tree:"
  button "Copy Code"
  code "await flow(container).findByRole("button", { name: "Delete account" }).click(); expect(container).toHaveTabSequence(['button "Cancel"', 'button "Delete"']);"
  heading "It catches what a screenshot can't" (level 2)
  paragraph
    text "A screenshot can be pixel-perfect while the page is broken for assistive technology. Swap a real"
    code "<button>"
    text "for a"
    code "<div onclick>"
    text "styled to match: identical screenshot, gone from the accessibility tree. That regression moves"
    strong "zero pixels"
    text ", so a visual snapshot sails right past it — an accessibility snapshot catches it immediately."
  paragraph
    text "Visual snapshots and accessibility snapshots are the two halves of regression testing —"
    emphasis "how it looks"
    text "and"
    emphasis "what it means"
    text "— and neither covers the other's blind spot."
